# tailscale-private-funnel

The Go implementation uses one executable with mode-specific top-level commands:

```sh
tailscale-private-funnel control join
tailscale-private-funnel control serve
tailscale-private-funnel gateway serve
tailscale-private-funnel router serve
```

Only `control join` opens the Bubble Tea bootstrap UI. Gateway and router join
commands are generated by the private control web UI and run non-interactively.
The control service stores settings in SQLite and encrypts provider and Tailscale
credentials with a local master key.

When paths are omitted, user-mode commands follow the Linux XDG layout:
Tailscale identity is stored under `${XDG_STATE_HOME:-~/.local/state}/tailscale-private-funnel/<mode>` and application data (SQLite, Caddy certificates, and config) under `${XDG_DATA_HOME:-~/.local/share}/tailscale-private-funnel/<mode>`. Set `--state-dir` and `--data-dir` for a system service or generated deployment path; no container-only directory is assumed.

The provider catalog exposes metadata for the pinned libdns provider list. The
control plane currently links runtime adapters for Cloudflare, GoDaddy, and
Route 53; other providers remain visible as unavailable until an adapter is
intentionally linked and contract-tested.

## DNS ownership safety

Every reconciliation lists the live provider records before it plans a write.
The installation ledger is the only authority for stale-record deletion. A
missing or failed provider listing is a hard error, and automatic router and
gateway reports never overwrite records outside their owner ID.

To migrate an existing record, first send the exact request with `dry_run:true`
to `/api/sync` or `/api/exposures/sync`. Review `existing_records`,
`desired_records`, and `remove`, then check the approval box in **Operations**
or send the returned short-lived `approval_token` with `allow_unowned:true`.
The token is bound to the provider, owner, live records, and ledger snapshot;
any change requires a new preview. The control plane transfers old ledger rows
only after the provider mutation succeeds and audits the explicit overwrite.

Router containers need the Docker socket group inside the container. On a
normal Ubuntu host, inspect the socket with `stat -c %g /var/run/docker.sock`
and pass that numeric value as `--group-add` alongside the router's non-root
UID. Keep the router on the dedicated ingress network. The router's tsnet
listener bridges its HTTP ingress on port `18080`, while Caddy's Docker label
proxy stays on the private ingress network.

## Router exposure policy and UI roles

The control UI is self-explanatory by mode: **Gateways** explains the public
ports, enrollment, certificate settings, and generated commands; **Routers**
explains the Docker socket, dedicated ingress network, supported labels, and
report behavior. Create a policy at **Exposure Policy** before starting a
router. The empty policy is default-deny.

Each enabled rule contains a full-hostname `hostname_regex` plus at least one
`roles` or `router_ids` selector. Optional `gateway_hostnames` limits the
gateway. Selectors can use a Tailscale user, `group:...`, `tag:...`,
`user:...`, or `node:...`. For example:

```json
{
  "rules": [
    {
      "name": "development routers",
      "hostname_regex": "[^.]+[.]dev[.]dlkn[.]dev",
      "roles": ["tag:router-dev"],
      "gateway_hostnames": ["gateway.dlkn.dev"],
      "enabled": true
    }
  ]
}
```

Tailscale `WhoIs` supplies the signed-in user's groups and the node's tags.
The control UI maps those selectors to three roles: `viewer` can read, an
`operator` can preview and run sync operations, and an `admin` can change
settings, providers, policies, enrollments, and nodes. Reports remain
node-authenticated and additionally require an enabled exposure-policy rule;
the UI role does not bypass that router policy.

Tailscale account Owner/Admin roles are admin-console roles, not a dependable
application claim in a `WhoIs` result. Use a Tailscale group, tag, node
selector, or custom app capability to map those people and service nodes to
the control roles.

Tagged service nodes do not inherit the human user who created them. For a
tagged node, grant a role through its `tag:...` selector, `node:...` selector,
or a custom Tailscale app capability. The **Access roles** page accepts a
capability name such as `example.com/cap/private-funnel`; the WhoIs capability
payload may contain `{"roles":["viewer"]}`, `operator`, or `admin`. The
control service ignores client-supplied role headers and rejects reserved
`tailscale.com/*` and `tailscale.io/*` custom capability names.

The same exposure policy is checked for signed router reports and the manual
router exposure endpoint. Operators cannot use the manual endpoint to bypass a
hostname or router selector; an administrator must first add a matching rule.
